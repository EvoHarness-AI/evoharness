# 功能建设顺序（Roadmap）

本文回答一件事：**接下来要做哪些功能，按什么顺序。**

不回答怎么做。落点不在这张表里重述：只在 `docs/structure.md` §7（某层何时允许出现）或 §9（迁移条件）已经有依据时引用它，否则写"待定"。本文与那份冲突时，以本文的**依赖关系**为准，以那份的**出现条件**为准。

对标口径分两步：①本仓与同级的常见编码 agent（Claude Code 系、kimi-code、opencode、nanocoder、gptme、penguin、Tianshu、cindy、FrontierAgent 等）逐项比对，收"别人有、我们没有"；②**每一项再回仓里核一遍已经有的那一半**，把"是什么"写成"已有 → 这一刀做什么"。第②步不能省：常见误判是只做第①步，于是把继承来的机制当成从零建设，依赖关系跟着一起错（审批被推到阶段三，而它的通道今天就在）。所以表里每一项都是**增量**，不是**缺口清单**，也不是**这个功能的全部**。

## 怎么读这张表

这张表是**某一天量出来的地图，不是任务系统**。代码与守卫是权威，本文是它们的转述。两者对不上时按代码开工，并在同一次改动里把这一行改对——**不要为了迁就本文的描述去改代码**。

- 每行的"已有"都带路径，那是量给当时的快照，腐烂得比排序快。动手前先复核那一格（`git ls-files` 加那几个文件），对不上就以仓库现状为准。
- **序**是阅读顺序，不是工单队列；**硬前置**是"我判断它成立的条件"，不是许可审批。判错了可以推翻，推翻时在"为什么在这个位置"留一句现实证据，让后来的人能重算。
- **内核档位**这一列只是人判的预判；机器判的那半见下面"三条约束"的第一条，最终归档在 §5.4 那一页。
- 文中的"不得 / 只准"分两种，读法不同。**带出处的**（`KERNEL.md` §3 与 §3.1、`structure.md` §8、D-012）是既有决定，权威在出处不在本文，去出处核一遍再动手；**不带出处的**只是本表的排序意见，可以被现实推翻。
- **本文没写不等于不能做。** 一个东西不在表里，通常只有两个原因：对标时没对出来，或者判断为不值得占一行。遇到第三种（新需求、新现实）直接按 `structure.md` §4 的决策树走，不用回来等表加行。
- 反过来也不成立：表里写了不代表已经做了、做好了。"这一刀"那一列全是**未**完成的承诺，不要当现状读。
- 这张表本身也可以被推翻。如果你（人或下一个代理）量出与它不同的依赖关系或代价，那就按你量到的做，并把改对的那一行留在同一次改动里——本文没有高于代码的地位，也不打算有。

## 排序用的三条判据

1. **先有"能力能自述"这一层**。绝大多数后续功能（审批、隔离、预算、子代理）的成立条件都是"某个能力声明了它要哪些权限"。这层不立，后面每一条闸门都只能靠约定俗成维持。**但缺的是声明，不是通道**：拦截与应答的机制已随内核继承下来（`tool_call` 钩子可 `{block, reason, terminate}`、`ctx.ui.select/confirm/input`、`ctx.isProjectTrusted()`）。所以第 1 项立住之后，第 2 项不需要等任何新机制。
2. **挂起与应答是一条机制，不是两条**；能拆就拆，因为两半的代价差一个档位。已有的一半：`ctx.ui.*` 在所有接口都能应答，RPC 侧带 timeout 与 AbortSignal，另有专门让宿主显示"在等人"的生命周期事件。剩下的两半：模型看得见它（第 6 项，A 档）、跨进程重启还接得上（第 11 项，B 档）。
3. **任何自主发起都排在审批之后**。无人值守时没有人工确认通道，只能按预先声明的权限放行或拒绝；顺序若颠倒，"先能自己跑、再补审批"必然退化成静默放行。本表把审批放在阶段一，是这条判据的直接推论，不是它的例外。

另外三条贯穿全表的约束：

- **每一刀先报内核档位**。`KERNEL.md` §3：A 加挂点 / B 改语义 / C 结构手术，档位写在每行的"内核档位"列上——**这一列只记人判的那一半**。"算不算动内核"不由本表维护：它是 `check:kernel-audit` 按 `KERNEL.md` §1 清单机器判的（`node scripts/check-kernel-audit.mjs --base main` 可本地先跑），在本表手抄 21 行对照只会随 P1–P3 搬家腐烂。注意后果：清单覆盖 `core/tools`、`core/extensions`、`core/compaction`、`packages/agent/src` 与 `project-trust.ts`、`trust-manager.ts` 等五个文件，所以**阶段一多数行都在清单内**，A 档也要同包带 `test/**` 改动，不带就 `npm run check` 红。
- **表内顺序是串行下界，不是禁止并行**。依赖拆成两列读：**硬前置** = 必须已完成才能开工；**可并行** = 不必等它做完，同期推进也行。并行时靠**代价**列挑：S = 一天内带测试完（先清它，因为它不值得占一次拍板），M = 一周内，L = 跨周或可能判 C。这一列是粗估，只用来排序，不当工期读。
- **只有一条内核**，另一条是封存的，见下节。任何一项都不准直接从封存件上取东西。

## 一条内核，一条封存的

- **在用的那条**：`packages/agent`（`@evoharness/agent-core` 的 `Agent` / `runAgentLoop`，目标态 `kernel/loop`）。全表的 turn、挂起、应答、恢复、主动发起都只能落在这条上。
- **封存的那条**：`packages/durable/src/harness/` —— 一条完整 loop 连同它的 `inbox`、`submissions`、`scheduler`、`task-graph`、`compaction`、`context`、`registry`、`usage`（单 `scheduler.ts` 实测 3158 行）。按 `docs/structure.md` §8 与 §3.6 它是**不启用的第二内核**，只有 `runtime-kit` 与 `env` 可以读它（§10 的 `check:package-layers` 第③条）。
- 两条推论：①**全表唯一的解封动作是 8b**——把封存件的 scheduler / task-graph 降格成 `runtime-kit` 的后端（§9 的 P2 行）。在那之前任何一项都不读它，包括"就借一下 scheduler"这种看起来无害的用法。②封存件里成套的东西（单写者 inbox、任务图、用量、检查点）会让后面几乎每一项都动"顺手拿过来"的念头——**这正是把它写进本表的原因**：要复用就走 8b 那条降格路径，不新开第二个口子。
- 三个挂点（`storage` / `schedule` / `turn_request`，即 8a）**不依赖封存件**：它们是 `KERNEL.md` §3.1 列出的纯 A 档加挂点，一行封存件代码都不必动。所以"只有一条内核"不等于"必须先动封存件才能往下做"——8a 就能解锁一批，这是把原来那一行拆成 8a / 8b 两行的理由。
- 归档分支（`archive/subagents-port`、`archive/web-port`）按 D-012 与偏离账本的身份是参考实现、需求规格、内容库，不是底座。引用它们写 D-xxx，不写分支内的文件路径。

## 明确不追（附翻转条件）

以下都是对标项目里的常见项，**当前判断是不追**。写出来是为了不用每次重新讨论。

| 不追 | 理由 | 什么情况下翻 |
|---|---|---|
| 桌面壳 / Web UI / IDE 插件 / ACP 协议 | 每一件都要同时养 UI 面 + 契约面 + 持久面三层，而这几面里没有任何一件已有第二个消费者 | 出现第二个真实消费者（比如确实要在编辑器里用，或确实要给外部程序调） |
| 语音输入 / 音频与多模态生成 | 单人使用场景下不改变工作形状 | 有明确的转写或语音输入需求，且愿意养 provider 与媒体管线 |
| Notebook 与 Office 富文档 | 依赖方向是文档处理，不是编码 | 日常工作里富文档读写占比真的上来 |
| 浏览器自动化与电脑控制 | 第 3 项（抓取/搜索）已覆盖绝大多数"上网看一眼"的需求，而这两个是数量级的实现成本 | 需要登录态、需要点击流程的任务成为日常主力 |
| 多渠道 IM 接入 | 属于交付面扩张，与能力增强无关 | 确实要在聊天工具里驱动它 |
| 第二个 agent 循环 | 单一循环是既有承诺，所有自主性都挂在扩展机制上。**注意这条红线今天已有具体形状**：`packages/durable/src/harness/` 就是那条不启用的第二内核，翻它的条件不是"要不要新写一条 loop"，而是"要不要解封它"——那是 8b 那一次动作，且只允许以"降格为 `runtime-kit` 后端"的形态发生 | 无（结构性红线，不翻转；解封的合法路径已由 8b 限定） |

## 与仓库现状的关系

- **封存件的守卫缺口要单开一刀，它的前置挂在 8b，不是待办。** `check:package-layers` 第③条只匹配 import 路径里的 `/harness`，而 `@evoharness/durable` 的根导出把 `Harness`、`InboxDoc`、`createRegistry`、scheduler 与 task-graph 的类型全 re-export 出来，依赖矩阵又允许 `capability → platform`。于是今天一个 `cap-*` 从根 barrel 读封存件不会红，"只有一个内核"只写在 §8 的文字里。8b 开工前先把这条拦实（`cap-*` / `feature-*` 不得依赖 durable 根导出，只准经 `runtime-kit`）。8a 不在这一刀下面：它用的 `durable/src/storage` 是清单外的 platform 代码，不是封存件，所以这条拦不拦得住都不阻塞 8a 解锁的那批；拦不住就老实记着拦不住，别在表里假设它已封好。
- **新工具命名要交代 stealth 表。** `packages/ai/src/api/anthropic-messages.ts` 在 OAuth token 下按 `claudeCodeTools` 改写工具名，查表键是 PascalCase 去形后的**无分隔小写**（`webfetch`、`todowrite`、`askuserquestion`）。本项目工具名是 snake_case（`structure.md` §6），所以 `web_fetch`、`todo_write`、`ask_user` 这类多词名**永远命不中**这张表。第 3、6、7、19 项要么显式加映射，要么显式记下"这几个工具不参与 stealth"；两边都不写，代价是将来排查行为差异的人从零猜。
- **已记录的坏不等于功能缺口。** 偏离账本里 D-004（`~/.pi` → `~/.evoharness` 没有迁移脚本，兜底一栏写着"无"）与 D-005（目录与版本端点指向未上线域名）是本仓自己承认的失效项，不进本表：它们是缺陷，走 issue 与对应档位（D-004 的迁移脚本按账本是 A 档）。本表只收"别人有、我们没有"的功能。
- 表里的顺序是**功能优先级**，不是文件迁移计划。既有代码往目标分层搬家是另一件事，只在"新契约 + 已有工具完成适配验证"这类条件真的满足时才做，不为结构好看而搬。但本表的第 1、4、8b、15、16 项各自踩在 `structure.md` §9 的某一行上（capability 契约、bash → `cap-shell`、harness 降格、evals、compaction 归属），开工时两处必须同时引用，改一处要改另一处——否则功能顺序和迁移条件会各漂各的。
- 从本表拾起某一项开工时，它要先过 `docs/structure.md` §5.4 的一页规格：本表只回答"要不要做、能不能做"，那一页回答"这一刀具体欠什么证据"。两份东西不重叠，不要拿本表当规格。每行"内核档位"列只是预判，最终以 §5.4 那页的归档为准；若那页判出的档位比这一格高（A 判成 B、B 判成 C），回到本表改这格，不在别处开口子。
- 也不为凑齐某项而写空壳验收（只断言接口存在、被假实现吞掉真实契约的那类）。差距如实记，不做假的"已完成"。
- 包数量会在阶段二前后越过当前门禁的告警阈值，届时对应的"是否要把测试按改动范围分车道"的规划条目会被叫醒，需要在同一次改动里给出结论（做 / 改条件 / 作废），不留红过夜。
