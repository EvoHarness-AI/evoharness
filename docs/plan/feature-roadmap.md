# 功能建设顺序（Roadmap）

本文回答一件事：**接下来要做哪些功能，按什么顺序。**

不回答怎么做、做完放在哪儿。`docs/structure.md` 的分层、包名与命名只是**参考**，不是最终形态；它和本文冲突时，以本文的**依赖关系**为准，落点另议。每个功能正式动手前，再单独定它的归属与实现。

对标口径分两步：①本仓与同级的常见编码 agent（Claude Code 系、kimi-code、opencode、nanocoder、gptme、penguin、Tianshu、cindy、FrontierAgent 等）逐项比对，收"别人有、我们没有"；②**每一项再回仓里核一遍已经有的那一半**，把"是什么"写成"已有 → 这一刀做什么"。第②步不能省：这张表原先就是只做了第①步，结果把继承来的机制当成从零建设，依赖关系跟着一起错（审批被推到阶段三，而它的通道今天就在）。所以表里每一项都是**增量**，不是**缺口清单**，也不是**这个功能的全部**。

---

## 排序用的三条判据

1. **先有"能力能自述"这一层**。绝大多数后续功能（审批、隔离、预算、子代理）的成立条件都是"某个能力声明了它要哪些权限"。这层不立，后面每一条闸门都只能靠约定俗成维持。**但缺的是声明，不是通道**：拦截与应答的机制已随内核继承下来（`tool_call` 钩子可 `{block, reason, terminate}`、`ctx.ui.select/confirm/input`、`ctx.isProjectTrusted()`）。所以第 1 项立住之后，第 2 项不需要等任何新机制。
2. **挂起与应答是一条机制，不是两条**。"模型反问用户"和"工具调用要人批"共用同一次挂起—应答。已有的一半：`ctx.ui.*` 在所有接口都能应答，RPC 侧带 timeout 与 AbortSignal，另有专门让宿主显示"在等人"的生命周期事件。剩下的只有：模型看得见它（加一个工具）、跨进程重启还接得上（这才动 turn 语义）。两件事的代价差一个档位，所以本表把它们拆成第 6 项和第 11 项。
3. **任何自主发起都排在审批之后**。无人值守时没有人工确认通道，只能按预先声明的权限放行或拒绝；顺序若颠倒，"先能自己跑、再补审批"必然退化成静默放行。这条判据在上一版表里自己没成立：审批排在第 10 位，而它的通道早就存在。

另外三条贯穿全表的约束：

- **每一刀先报内核档位**（`KERNEL.md` §3：A 加挂点 / B 改语义 / C 结构手术），档位写在每行的"内核"列上。全表只有两处真的碰内核：第 8 项（A 档挂点 + 封存件降格）与第 11 项（B 档 turn 推进语义）。上一版说"动内核的机会只有一次，就是第 7 项"两头都不准：那一刀按 §3.1 是 A 档，不是语义改动；而被称作"风险最低"的那一刀，真正的内核改动在它身上。
- **表内顺序是串行下界，不是禁止并行**。依赖拆成两列读：**硬前置** = 必须已完成才能开工；**可并行** = 不必等它做完，同期推进也行。
- **只有一条内核**，另一条是封存的，见下节。任何一项都不准直接从封存件上取东西。

## 一条内核，一条封存的

- **在用的那条**：`packages/agent`（`@evoharness/agent-core` 的 `Agent` / `runAgentLoop`，目标态 `kernel/loop`）。全表的 turn、挂起、应答、恢复、主动发起都只能落在这条上。
- **封存的那条**：`packages/durable/src/harness/` —— 一条完整 loop 连同它的 `inbox`、`submissions`、`scheduler`、`task-graph`、`compaction`、`context`、`registry`、`usage`（单 `scheduler.ts` 138KB）。按 `docs/structure.md` §8 与 §3.5 它是**不启用的第二内核**，只有 `runtime-kit` 与 `env` 可以读它（`check:package-layers` 第③条）。
- 由此定死两条：①**全表唯一的解封动作是第 8 项**——把封存件的 scheduler / task-graph 降格成 `runtime-kit` 的后端（§9 的 P2 行），并把三个挂点挂上 kernel。解封之前任何一项都不读它，包括"就借一下 scheduler"这种看起来无害的用法。②封存件里成套的东西（单写者 inbox、任务图、用量、检查点）会让后面几乎每一项都动"顺手拿过来"的念头——**这正是把它写进本表的原因**：要复用就走第 8 项那条降格路径，不新开第二个口子。
- 归档分支（`archive/subagents-port`、`archive/web-port`）按 D-012 与偏离账本的身份是参考实现、需求规格、内容库，不是底座。引用它们写 D-xxx，不写分支内的文件路径。

## 明确不追（附翻转条件）

以下都是对标项目里的常见项，**当前判断是不追**。写出来是为了不用每次重新讨论。

| 不追 | 理由 | 什么情况下翻 |
|---|---|---|
| 桌面壳 / Web UI / IDE 插件 / ACP 协议 | 每一件都要同时养 UI 面 + 契约面 + 持久面三层，而这几面里没有任何一件已有第二个消费者 | 出现第二个真实消费者（比如确实要在编辑器里用，或确实要给外部程序调） |
| 语音输入 / 音频与多模态生成 | 单人使用场景下不改变工作形状 | 有明确的转写或语音输入需求，且愿意养 provider 与媒体管线 |
| Notebook 与 Office 富文档 | 依赖方向是文档处理，不是编码 | 日常工作里富文档读写占比真的上来 |
| 浏览器自动化与电脑控制 | 第 3 项（抓取/搜索）已覆盖绝大多数"上网看一眼"的需求，而这两个是数量级的实现成本 | 需要登录态、需要点击流程的任务成为日常主力 |
| 多渠道 IM 接入 | 属于交付面扩张，与能力增强无关 | 确实要在聊天工具里驱动它 |
| 第二个 agent 循环 | 单一循环是既有承诺，所有自主性都挂在扩展机制上。**注意这条红线今天已有具体形状**：`packages/durable/src/harness/` 就是那条不启用的第二内核，翻它的条件不是"要不要新写一条 loop"，而是"要不要解封它"——那是第 8 项那一次动作，且只允许以"降格为 `runtime-kit` 后端"的形态发生 | 无（结构性红线，不翻转；解封的合法路径已由第 8 项限定） |

## 与仓库现状的关系

- **封存件的守卫缺口是第 8 项的前置，不是待办。** `check:package-layers` 第③条只匹配 import 路径里的 `/harness`，而 `@evoharness/durable` 的根导出把 `Harness`、`InboxDoc`、`createRegistry`、scheduler 与 task-graph 的类型全 re-export 出来，依赖矩阵又允许 `capability → platform`。于是今天一个 `cap-*` 从根 barrel 读封存件不会红，"只有一个内核"只写在 §8 的文字里。第 8 项开工前先把这条拦实（`cap-*` / `feature-*` 不得依赖 durable 根导出，只准经 `runtime-kit`），拦不住就老实记着拦不住，别在表里假设它已封好。
- **新工具命名要交代 stealth 表。** `packages/ai/src/api/anthropic-messages.ts` 在 OAuth token 下按 `claudeCodeTools` 改写工具名，查表键是 PascalCase 去形后的**无分隔小写**（`webfetch`、`todowrite`、`askuserquestion`）。本项目工具名是 snake_case（`structure.md` §6），所以 `web_fetch`、`todo_write`、`ask_user` 这类多词名**永远命不中**这张表。第 3、6、7、19 项要么显式加映射，要么显式记下"这几个工具不参与 stealth"；两边都不写，代价是将来排查行为差异的人从零猜。
- **已记录的坏不等于功能缺口。** 偏离账本里 D-004（`~/.pi` → `~/.evoharness` 没有迁移脚本，兜底一栏写着"无"）与 D-005（目录与版本端点指向未上线域名）是本仓自己承认的失效项，不进本表：它们是缺陷，走 issue 与对应档位（D-004 的迁移脚本按账本是 A 档）。本表只收"别人有、我们没有"的功能。
